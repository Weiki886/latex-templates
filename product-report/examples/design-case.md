# 智衡产品设计案

> **一句话摘要：** 智衡 ZhiHeng 是一名证据约束的复杂售后办理 Agent：先问清事实，依据产品知识和业务 SOP 作出判断，满足条件时调用工具完成办理；证据不足、规则冲突或工具失败时停止执行并诚实升级。

## 1. 问题是什么：动机与用户故事

### 1.1 官方命题

主办方将智能客服能力分为三个阶段：L1 从知识库回答问题，L2 多轮追问并引导操作，L3 调用后端系统完成退款、换货、派单等业务。主办方已经具备 L3 能力，本赛题要求参赛者继续解决复杂售后中的五个难点：看图、问清、分流、接稳和防幻觉。

官方对作品的要求不是“做一个会聊天的客服”，而是交付一个能够独立接住求助、沿完整售后链路处理，并通过现场交互证明结果的 AI 客服 Agent。官方同时强调：检索不到时应诚实升级，不能伪造排障结果、质保承诺或召回答案。

### 1.2 用户故事

**故事一（官方描述）。** 用户只说“我的 X1 Pro 不吸了”。同一名称可能对应不同产品，故障现象也没有被说清。若系统直接给出步骤，可能从一开始就进入错误流程。

**故事二（官方渠道差异）。** 用户在品牌自有系统中查不到订单，实际可能来自经销商。Agent 需要结合授权经销商名录和适用政策判断后续路径，不能因为查不到订单就直接拒绝，也不能无依据承诺质保。

**故事三（公开用户经历）。** 2025 年 12 月，一位 智能硬件品牌用户称先前获得的替换预期在后续沟通中没有兑现。该个案不能证明品牌整体问题，但说明售后场景中“生成一句承诺”和“规则允许且能够执行”是两件不同的事。

### 1.3 问题定义

这些场景的共同问题是：**AI 在事实尚未确认、知识适用范围不明或业务规则不满足时，仍可能继续回答、路由或办理。**

> 面向需要多轮诊断和业务办理的智能硬件售后用户：产品、故障、订单、渠道、地区或政策信息缺失时，AI 可能给出不适用的排障步骤、错误流程或无依据承诺。用户需要一名知道何时追问、依据什么判断、满足什么条件才能执行，并在无法执行时明确停下的售后 Agent。

这仍是待验证的问题假设。公开材料不能证明主办方现有系统在哪个具体环节存在缺口，也不能替代官方脱敏工单、知识库和 SOP。

## 2. 用户是谁

**主要用户：** 遇到非简单智能硬件售后问题，需要经过多轮诊断、规则判断或业务办理才能获得结果的消费者。

**相关角色：**

- 在 Agent 无法安全完成任务时接手问题的客服或技术支持人员；
- 维护产品知识、业务 SOP、经销商名录和办理规则的业务人员；
- 评估 Agent 是否可以在真实业务中使用的客服与产品负责人。

第一版不同时服务所有角色。用户侧交互是主体；业务人员视角只展示证据、规则和工具执行所需的最小信息；人工接手仅作为失败或审批路径。

## 3. 为什么值得做：现有做法及其不足

### 3.1 市面上的做法

| 做法 | 代表产品 | 已公开能力 | 对本方案的启示 |
| --- | --- | --- | --- |
| 产品化自助排障 | 海外自助排障产品 | 产品识别、逐步流程、设备上下文、人工升级 | 单纯多轮引导和转人工已经存在，不能成为主要创新 |
| 视觉支持 | 视觉远程支持产品 | 图片理解、视觉引导、远程支持 | 图片必须转化为可用于诊断的证据，通用识图不够 |
| 流程与工具执行 | 海外客服平台的流程自动化与 Agent 能力 | 条件流程、数据连接器、字段更新和升级策略 | 工具调用需要条件、参数和错误处理，不能只展示函数调用 |
| 工单与服务流转 | 国内工单与服务流转系统 | 工单字段、自动分配、流程流转 | 工单系统不是本赛题的核心交付对象 |

这些公开资料证明相关能力已经存在，但不能证明它们在主办方目标场景中的效果，也不能据此声称智衡优于现有产品。

### 3.2 我们选的方向

智衡采用 **“一个主方向、两个核心辅助、两个轻量能力”** 的组合：以“防幻觉”为主方向，以“问清”和“分流”为核心辅助，以“看图”和“接稳”为轻量能力。防幻觉包含四层约束：

1. **事实约束：** 用户自述、系统推断、已确认事实和系统读取信息分开；
2. **知识约束：** 排障建议必须关联适用的产品知识；
3. **规则约束：** 业务决策必须关联适用的 SOP、渠道和地区条件；
4. **执行约束：** 工具调用前校验前置条件，调用后以真实回执更新结果。

五个方向按同一链路协作：**问清事实，看图补充证据，分流到正确流程，防幻觉机制约束判断与执行，接稳用户情绪并反馈结果。** 它们不是五个同等规模的模块；产品创新、主要开发投入和验收标准仍然集中在防幻觉。

| 层级 | 方向 | 在产品中的作用 | 第一版边界 |
| --- | --- | --- | --- |
| 主方向 | 防幻觉 | 约束事实、知识、规则、工具参数和执行结果 | 贯穿全部演示路径 |
| 核心辅助 | 问清 | 补齐诊断和办理所需事实 | 动态追问并解释原因 |
| 核心辅助 | 分流 | 根据诉求、渠道、地区和 SOP 进入正确流程 | 实现有限且可验证的流程分支 |
| 轻量能力 | 看图 | 提取可核验的故障线索 | 不做通用视觉诊断 |
| 轻量能力 | 接稳 | 承接紧迫、不满与失败情绪 | 规则级识别与分层表达 |

### 3.3 为什么值得验证

- 官方将幻觉描述为售后场景的核心痛点，关注 Agent 是否按规则执行，而不是自由发挥；
- 约七成售后被官方归为复杂问题，涉及多品类诊断、多渠道和多地区政策判断、退换货决策；
- 主办方已经具备 L3 办理能力，继续提高业务动作的准确性、可控性和可复核性，比重新建设问答或工单系统更贴合赛题；
- 团队具备 Agent 编排、RAG、HITL 高风险操作拦截、证据链前端和完整测试能力，能够在比赛原型中形成可见差异。

以上是选择方向的依据，不是效果证明。真实价值需要用官方数据和同任务对照验证。

### 3.4 方案价值与预期效果

- **售后用户：** 在信息不完整时获得有目的的追问，并能看到当前状态、判断依据和下一步；通过重复追问、无依据回答、错误流程进入和结果状态错误进行验证。
- **客服与技术支持：** Agent 无法继续时提供事实、证据、规则、已执行步骤和阻塞原因；通过升级信息完整率及人工重新询问的关键事实数进行验证。
- **售后业务：** 业务动作经过证据、规则和执行三道校验，用户可见状态与工具回执保持一致；通过不安全动作拦截率、工具结果一致率和任务结果准确率进行验证。

这些内容是待验证的预期效果，不是已经取得的业务提升。具体样本、基线和目标值需在获得官方脱敏工单、知识库与 SOP 后确定；预赛阶段先说明指标定义和验证方法，不虚构提升比例。24 小时内的可演示范围见第 7 节。

## 4. 怎么做：关键决策与依据

### 4.1 决策一：以“防幻觉”为主，四个方向分层辅助

| 备选 | 取舍理由 |
| --- | --- |
| 看图 | 展示效果强，但高度依赖配套图片与故障答案；作为轻量证据输入 |
| 问清 | 是所有后续处理的前提，但单独做容易停留在 L2；作为核心辅助能力 |
| 分流 | 接近 L3 业务决策，但依赖经销商名录和 SOP；作为核心辅助能力，纳入办理路径 |
| 接稳 | 重要但容易退化为话术优化；作为轻量能力，纳入紧迫、投诉风险和失败路径 |
| **防幻觉** | **选择。能够把事实、知识、规则和工具执行串成完整链路，直接证明“该办的事办得成，不该办的事不乱来”** |

### 4.2 决策二：核心产物是“可验证的服务任务”，不是接力卡

服务任务持续记录用户目标、必需事实、证据、规则条件、已执行步骤、工具请求、工具回执和真实状态。它既驱动 Agent 的下一步，也为界面展示、评估和失败升级提供统一数据源。

服务接力卡仍然保留，但只在以下情况生成：知识无覆盖、规则冲突、工具失败、权限不足、需要人工审批或用户明确要求人工。它是服务任务在升级时的结构化快照，不是产品主体。

### 4.3 决策三：主场景暂定“派对前智能音箱故障”

选择理由：官方示例提供了同类场景；时间压力可以自然展示情绪承接；图片可作为线索输入；排障步骤可枚举；排障失败后可以连接一条受规则约束的维修、换货或派单路径。

具体产品、故障、政策和业务动作仍需等待官方数据。若官方资料不覆盖该品类，必须替换场景，不能为了保留脚本编造知识。

### 4.4 决策四：业务动作必须经过“证据—规则—执行”三道门

| 关口 | 必须回答的问题 | 不满足时的行为 |
| --- | --- | --- |
| 证据门 | 产品、故障、订单、渠道、地区等必需事实是否确认？ | 继续追问或读取系统信息 |
| 规则门 | 当前知识和 SOP 是否适用，是否存在冲突或越权？ | 停止决策，说明缺口或进入人工审批 |
| 执行门 | 工具参数是否合法，执行环境与权限是否允许？ | 阻止调用或返回已阻塞 |

工具调用完成后还必须检查回执。只有工具明确返回完成，才能说业务已经办成；返回已接受、排队中或失败时，界面必须保持对应状态。

### 4.5 决策五：结果状态反映业务事实

第一版状态定义为：信息收集中、排障中、待执行、办理中、已解决、已升级、已阻塞。

- 排障成功只有在用户确认恢复后进入“已解决”；
- 业务申请已提交但尚未完成时进入“办理中”；
- 工具失败、权限不足或规则冲突进入“已阻塞”；
- 无法安全继续并进入人工流程时进入“已升级”。

### 4.6 研究依据如何转化为产品机制

论文在本方案中用于说明设计依据，不作为产品效果证明。智衡采用的是与赛题相关的机制原则，再结合官方产品知识、业务 SOP、工具接口和 24 小时开发约束进行裁剪。

| 研究来源 | 论文中的关键点 | 智衡采用的设计点与裁剪边界 |
| --- | --- | --- |
| [**Self-RAG**](https://arxiv.org/abs/2310.11511)（ICLR 2024） | 固定检索并不总是有益；模型可以按需检索，并对检索内容的相关性、回答的证据支持度和整体有效性进行自我评估 | 采用“需要时检索”和“回答前检查证据支持度”的原则：知识或规则无覆盖时停止给出确定结论。首版不训练带 reflection token 的新模型，而以工作流节点和结构化校验实现 |
| [**Corrective Retrieval Augmented Generation**](https://arxiv.org/abs/2401.15884)（2024） | 在生成前评估检索结果质量，并根据置信程度触发不同的纠错动作；同时过滤检索内容中的无关信息 | 在知识检索后增加相关性、适用范围和冲突检查，将结果分为可用、需补证据和不可用。CRAG 使用 Web 搜索扩展知识，智衡涉及企业售后规则，因此不可用时选择补问、限定回答或升级人工，不使用公开网页替代官方 SOP |
| [**ReAct**](https://arxiv.org/abs/2210.03629)（ICLR 2023） | 将推理与面向外部环境的行动交替组织，使系统能够根据知识库或工具返回的信息更新后续计划并处理异常 | 采用“判断—行动—观察回执—更新状态”的执行循环：工具结果必须回到服务任务后才能决定下一步。界面只展示事实、依据、校验结果和操作记录，不展示或声称获取模型的隐藏思维链 |
| [**ClarQ**](https://aclanthology.org/2020.acl-main.651/)（ACL 2020） | 对话和问答系统面对歧义时需要生成澄清问题；论文通过大规模澄清问题数据证明该任务能够改善后续问答 | 将“问清”实现为由必需事实清单驱动的澄清：只追问会改变诊断、分流或办理条件的信息，并记录已确认事实，避免重复追问。首版不复现 ClarQ 的数据构建和训练方法 |
| [**Consistent Estimators for Learning to Defer to an Expert**](https://arxiv.org/abs/2006.01862)（ICML 2020） | 系统可以在自行预测与交由下游专家判断之间作出选择，而不是要求模型处理所有输入 | 将人工升级定义为一种正确结果：证据不足、规则冲突、权限不足或高风险动作需要审批时，Agent 停止执行并提交结构化接力信息。首版使用显式业务规则触发升级，不声称训练了论文中的 classifier 与 rejector |

这些研究共同支撑一条产品原则：**Agent 的价值不只是生成答案，而是在信息不完整、知识可能失配和工具可能失败时，仍能选择可验证的下一步。** 最终机制是否有效，仍需用官方数据和同任务对照测试验证。
:::

### 4.7 方案优势与创新点

1. **把防幻觉落实到业务执行。** 智衡同时约束事实、知识、规则、工具参数和执行结果，业务动作只有通过证据门、规则门和执行门后才会发生。
2. **用同一动作的允许与拦截形成可见对照。** 演示在条件完整时安全办理，在条件缺失或规则冲突时停止执行，使评委能够直接观察约束是否生效。
3. **用服务任务贯通完整售后链路。** 必需事实、证据、规则、操作记录、工具回执和结果状态保存在同一个任务对象中，既驱动 Agent，也支撑前端解释、验收和人工接手。

## 5. 基本概念与信息结构

### 5.1 服务任务（Service Task）

服务任务是 Agent 处理一次用户求助的核心对象：

| 分区 | 主要内容 | 约束 |
| --- | --- | --- |
| 用户目标 | 求助事项、期望结果、时间约束 | 保留用户原始表达 |
| 必需事实 | 产品、故障、订单、渠道、地区等 | 按目标动作动态生成，不做无关收集 |
| 信息与证据 | 用户自述、系统推断、已确认事实、知识与规则 | 每条保留来源、适用范围和状态 |
| 处理记录 | 排障步骤、用户反馈、时间和结果 | 已执行步骤不重复推荐 |
| 决策记录 | 候选动作、选择理由、规则校验 | 业务动作必须关联 SOP |
| 工具执行 | 工具名、参数、环境、请求与回执 | 参数只取已确认事实 |
| 当前状态 | 七类状态之一及下一步 | 不把对话结束当作解决 |
| 风险与升级 | 情绪、冲突、缺口、审批和人工接手信息 | 只在需要时生成接力卡 |

### 5.2 七阶段处理链路

**建立任务、补齐事实、形成证据、诊断与分流、安全决策、工具执行、结果确认或升级。**

每个阶段都产生结构化输出并成为下一阶段的输入。Agent 不能绕过前置条件直接调用高风险工具，也不能用模型推断填充关键业务参数。

### 5.3 服务接力卡

接力卡是升级时的结构化快照，包含用户目标、已确认事实、用户自述、系统推断、知识和规则证据、已执行步骤、工具调用与回执、阻塞原因、待核实事项以及情绪与风险。

接力卡的价值是帮助人工理解“为什么 Agent 停下”，并从真实断点继续；它不再承担整个产品的差异化叙事。

### 5.4 执行环境

Demo 中每次业务动作必须标明执行环境：

- **真实：** 调用官方开放的真实业务接口；
- **沙箱：** 调用官方或团队搭建的隔离测试接口；
- **模拟：** 使用明确标注的本地 Mock，只证明流程与状态处理。

模拟执行不能在界面或路演中描述为真实办理成功。

### 5.5 示例契约（待官方 SOP 验证）

以下契约只用于说明实现方式，不代表主办方真实接口或政策。官方资料到位后必须按正式 SOP、名录和接口文档重写。

| 契约项 | 示例设计 | 安全约束 |
| --- | --- | --- |
| 服务任务字段 | `goal`、`product`、`symptom`、`order_channel`、`region`、`facts`、`evidence`、`steps`、`decision`、`tool_calls`、`status`、`handoff` | 每个字段保留来源；`facts` 只放已确认事实，推断不得进入关键参数 |
| 示例工具 | `create_after_sales_request` | 仅当前置条件全部通过且用户确认后允许调用；真实、沙箱、模拟环境必须分别标识 |
| 前置条件 | 产品已确认、故障现象已确认、订单渠道已确认、地区已确认、必需排障已完成、SOP 已匹配且无冲突 | 任一条件缺失时进入补问、已阻塞或已升级，不生成业务承诺 |
| 允许参数 | `product_id`、`issue_code`、`order_channel`、`region`、`request_type`、`evidence_refs` | 参数只能引用已确认事实和规则证据；禁止用模型自由文本填充关键字段 |
| 回执状态 | `accepted`、`processing`、`completed`、`failed` | 只有 `completed` 可表述为办理完成；`accepted/processing` 保持办理中，`failed` 进入已阻塞或升级 |

## 6. 三个核心功能与本期边界

为便于评审快速理解，智衡将五个赛题难点收束到同一条服务链路中的三个核心功能，而不是拆成五套独立模块。底层机制在《产品方案与核心能力》中拆为精准问清、多源证据、规则分流与工具执行、真实结果状态四类。

::: {.capability-table colwidths="0.18,0.29,0.35,0.14"}
| 核心功能 | 做什么 | AI 如何发挥作用 | 约束与对应难点 |
| --- | --- | --- | --- |
| 事实澄清与证据构建 | 面对含糊描述或图片输入，识别产品、故障、订单、渠道、地区等缺失事实，提出会改变后续判断的必要问题，并形成可追溯证据 | 识别用户目标与实体，从图片提取候选故障线索，区分用户自述、系统推断和已确认事实；已确认信息不重复询问 | 以问清为核心，轻量使用看图；从输入阶段降低幻觉风险 |
| 证据约束的诊断与分流 | 检索适用的产品知识、业务 SOP 和授权经销商信息，检查相关性、适用范围与冲突，再选择排障或办理路径 | 用语义检索召回候选依据，由 Agent 结合任务上下文形成候选判断；明确规则负责渠道、地区、权限等硬边界 | 以分流为核心；知识无覆盖或规则冲突时禁止形成确定结论 |
| 安全办理与结果闭环 | 校验前置条件和工具参数，经用户确认后调用业务工具；根据真实回执更新状态，失败或无法继续时说明原因并升级 | 编排工具选择、参数生成和异常处理，将工具回执转换为办理中、已解决、已阻塞或已升级等业务状态，并生成必要的接力信息 | 以防幻觉为主方向，轻量承接情绪；不把调用请求等同于办理完成 |
:::

**本期明确不做：**

- 不做完整客服平台、工单系统、CRM 或运营后台；
- 不覆盖全部产品、国家、渠道和售后政策；
- 不把五个难点平均做成五套功能；
- 不训练通用视觉诊断或情绪分类模型；
- 不在无正式 SOP 时编造质保、退款、换货或召回规则；
- 不把模拟工具包装成真实业务接口；
- 不以会话摘要、转人工或服务接力卡作为主要创新；
- 不把调用请求成功等同于业务办理完成。

## 7. 原型与 Demo（先文字，后原型）

本文先明确解决什么问题、需要什么能力、边界在哪里；决赛现场原型的可演示范围与验收口径以本节为准。

### 7.1 24 小时可演示原型

24 小时集中开发以一个官方资料能够支撑的智能硬件售后场景为边界，接入有限的产品知识、业务 SOP 和工具接口。若官方没有开放真实写入接口，则使用明确标注的沙箱或本地 Mock，只验证 Agent 编排、规则拦截、状态处理和交互过程。

> **用户求助 $\rightarrow$ 建立任务 $\rightarrow$ 补齐事实与图片证据 $\rightarrow$ 检索知识与 SOP $\rightarrow$ 规则校验 $\rightarrow$ 工具执行 $\rightarrow$ 结果确认；任一关口不满足时进入补问、阻塞或人工升级。**

可演示交付物包括三个交互视图、三条任务路径、一组可核对的知识与规则样本，以及正常回执、失败回执和安全拦截状态。原型不承担全品类、全渠道和生产级客服平台建设。

### 7.2 三个交互视图

Demo 包含三个视图：

- **V1 用户服务视图：** 对话、图片输入、精准追问、分步排障、状态和结果确认；
- **V2 Agent 证据与决策视图：** 信息来源、必需事实、知识与 SOP、规则校验和工具记录；
- **V3 业务结果与升级视图：** 执行环境、工具回执、用户下一步和失败时的服务接力卡。

### 7.3 三条任务路径

三条演示路径：

- **P1 排障解决：** 重点展示问清，轻量展示看图；依据知识完成排障后由用户确认恢复；
- **P2 安全办理：** 重点展示分流与防幻觉；补齐业务事实，通过规则校验并调用工具，展示回执；
- **P3 诚实拦截：** 重点展示防幻觉，轻量展示接稳；条件缺失或规则无依据时禁止调用工具，承接情绪、说明原因并升级人工。

路演核心画面并排展示 P2 和 P3：同一个业务动作在条件完整时被允许，在条件缺失时被拦截。差异来自证据和规则，不是两段预写话术。

## 8. 怎么验收

### 8.1 产品定义验收

- 明确采用“防幻觉主攻、问清与分流核心辅助、看图与接稳轻量辅助”的层级，没有把五个难点平均铺开；
- 产品主体是可办理业务的 AI 客服 Agent，不是接力卡或工单系统；
- 问清、知识、规则、工具和结果形成完整链路；
- 真实、沙箱与模拟执行边界清楚；
- 成功、处理中、阻塞、升级和用户问题解决不会混为一谈。

### 8.2 Demo 验收

- P1、P2、P3 三条路径均可交互走通；
- P2 在工具调用前完成必需事实与规则校验，调用后展示工具回执；
- P3 的不安全动作被拦截，没有编造政策或办理结果；
- 所有关键事实和决策能够追溯来源；
- 服务接力卡只在升级或审批路径出现。

### 8.3 自评口径（团队内部，非官方指标）

必需事实完整率、证据覆盖率、不安全动作拦截率、工具结果一致率、任务结果准确率、无依据回答数。具体样本和目标值需在取得官方数据后确定，不提前虚构提升比例。
